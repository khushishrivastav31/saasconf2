# Internationalization (i18n)

This document covers the i18n subsystems used across backend and frontend: timezone handling, accent-insensitive search, locale-aware formatting, phone validation, and address formatting.

## Quick Reference

| Subsystem | Backend | Frontend |
|-----------|---------|----------|
| Timezone | `app.core.utils.utcnow()` | -- |
| Search | `app.core.search.unaccent_ilike()` | -- |

## Timezone Handling

**Rule: never use `datetime.utcnow()`.** It returns a naive (timezone-unaware) datetime, which causes comparison errors with timezone-aware values from the database.

### Usage

```python
from app.core.utils import utcnow

now = utcnow()  # returns datetime.now(timezone.utc)
```

All `DateTime` columns in models use `timezone=True`:

```python
created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())
```

When decoding JWT timestamps (which are epoch integers), use:

```python
from datetime import datetime, timezone

expiry = datetime.fromtimestamp(payload["exp"], tz=timezone.utc)
```

Never use `datetime.utcfromtimestamp()` -- it also returns naive datetimes.

**Source:** `backend/app/core/utils.py`

## Accent-Insensitive Search

Search queries use PostgreSQL's `unaccent` extension so that "cafe" matches "Cafe", "muller" matches "Muller", etc.

### Prerequisites

- **Migration 077** creates the extension: `CREATE EXTENSION IF NOT EXISTS unaccent`
- **Test setup:** `backend/tests/conftest.py` creates the extension manually because tests use `Base.metadata.create_all` instead of Alembic migrations
- The `postgres:15-alpine` image used in CI includes the extension

### Usage

```python
from app.core.search import unaccent_ilike

# In an endpoint with a search parameter:
if search:
    query = query.where(
        unaccent_ilike(Model.name, search)
        | unaccent_ilike(Model.city, search)
    )
```

The helper wraps both the column and term with `unaccent()` and uses `ILIKE` with `%` wildcards:

```python
def unaccent_ilike(column, term):
    return func.unaccent(column).ilike(func.unaccent(f"%{term}%"))
```

### Adding search to a new endpoint

1. Import: `from app.core.search import unaccent_ilike`
2. Add a `search: str | None = None` query parameter
3. Apply: `query = query.where(unaccent_ilike(Column, search))`
4. For multi-column search, combine with `|` (OR)

### E2E test

`frontend/e2e/accent-search.spec.ts` tests accent search via the Sponsors API. It creates a sponsor with accented names ("Cafe Francois Muller", city "Munchen") and verifies unaccented search terms find it.

**Source:** `backend/app/core/search.py`

## Conference Locale

Each conference has a `locale` field (BCP 47 tag like `"en"`, `"de"`, `"es"`) that drives locale-aware formatting.

### Backend

```python
# Model (backend/app/models/conference.py)
locale: Mapped[str | None] = mapped_column(String(10), nullable=True, default="en")
```

Migration 078 added this column with a default of `'en'`.

### Frontend date formatting

Use the helpers in `frontend/src/utils/formatDate.ts`:

```typescript
import { formatDate, formatDateTime, formatTime } from "../utils/formatDate";

formatDate("2026-02-13", "de")     // "13.02.2026"
formatDate("2026-02-13", "en")     // "Feb 13, 2026"
formatDateTime("2026-02-13T15:30") // "Feb 13, 2026, 3:30 PM"
formatTime("2026-02-13T15:30")     // "3:30 PM"
```

These use `Intl.DateTimeFormat` internally. The browser handles all locale-specific rules (month names, date order, 12/24h clock). If formatting fails, they fall back to `String(date)`.

### Where to get the locale

In conference-scoped pages, pass `conference.locale` to the formatter. For pages without conference context (admin panels, portal), use the default `"en"`.

**Sources:** `backend/app/models/conference.py`, `frontend/src/utils/formatDate.ts`

## Phone Validation

Phone numbers are validated using Google's libphonenumber library on both backend and frontend.

### Format requirements

- Must include `+` country code prefix (e.g., `+49123456789`)
- The `00` prefix (e.g., `00491234...`) is **not** accepted
- Spaces and dashes are allowed (e.g., `+49 170 123 4567`)
- Empty/null values are valid (phone fields are optional)

### Backend

`backend/app/core/validators.py` validates **and normalizes** to E.164:

```python
from app.core.validators import validate_phone

validate_phone("+49 170 123 4567")  # returns "+491701234567" (E.164)
validate_phone("invalid")           # raises ValueError
validate_phone(None)                # returns None
validate_phone("")                  # returns ""
```

Used in Pydantic schemas via `@field_validator`:

```python
@field_validator("phone")
@classmethod
def check_phone(cls, v: str | None) -> str | None:
    return validate_phone(v)
```

**Dependency:** `phonenumbers` (in `backend/requirements.txt`)

### Frontend

`frontend/src/utils/validators.ts` validates but does **not** normalize:

```typescript
import { validatePhone } from "../utils/validators";

validatePhone("+491701234567")  // null (valid)
validatePhone("invalid")       // "Invalid phone number..." (error message)
validatePhone("")              // null (valid, optional)
```

**Dependency:** `libphonenumber-js` (in `frontend/package.json`)

### Data migration gotcha

The phone validator runs on Pydantic model construction, including response objects. If existing database records contain phone numbers that were valid under the old regex validator but invalid under libphonenumber (e.g., `+491111111` -- too short for Germany), the API will return a 500 error.

**Fix:** update invalid phone data in the database. Numbers missing the `+` prefix can often be fixed by prepending it. Completely invalid numbers should be set to NULL.

**Sources:** `backend/app/core/validators.py`, `frontend/src/utils/validators.ts`

## Address Formatting

`backend/app/core/address.py` formats addresses according to country conventions.

### Supported countries

| Country code | Format |
|-------------|--------|
| DE, AT, CH | Street, PostalCode City, Country |
| US, CA | Street, City, State ZIP, Country |
| GB | Street, City, Postcode, Country |
| FR, BE, NL | Street, PostalCode City, Country |
| JP | PostalCode, State City, Street, Country |

Unknown countries fall back to comma-separated format.

### Usage

```python
from app.core.address import format_address

format_address(
    address_line1="Hegelallee 12",
    city="Potsdam",
    postal_code="14467",
    country="Germany",
)
# "Hegelallee 12\n14467 Potsdam\nGermany"
```

The function accepts country names (English or native: "Germany", "Deutschland") and resolves them to ISO codes internally.

### Adding a new country format

1. Add the template to `_FORMATS` in `backend/app/core/address.py`
2. Add name mappings to `_COUNTRY_CODES`
3. Blank lines and trailing commas are stripped automatically

### Integration

The `Location` model uses `format_address()` in its `full_address` property.

**Source:** `backend/app/core/address.py`

### Test database

Tests use `Base.metadata.create_all` (not Alembic), so the unaccent extension is created explicitly in `backend/tests/conftest.py`:

```python
async def _create_tables() -> None:
    async with test_engine.begin() as conn:
        await conn.execute(text("CREATE EXTENSION IF NOT EXISTS unaccent"))
        await conn.run_sync(Base.metadata.create_all)
```

If you add another PostgreSQL extension, add it here as well.
